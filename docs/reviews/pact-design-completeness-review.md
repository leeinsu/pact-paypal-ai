# PACT 수정안 설계 완성도 재평가

평가일: 2026-10-20. 대상: [설계 수정안](../pact-revision-proposal.md).
대상 SHA-256: `a043ac470588b87c9b6fb2a232d7955b47f667281772bc61d7f0b35e2f37422f`.
독립 검토: `pact_design_only_review` / `metis`. 주 에이전트가 근거를 대조하고 결과를 정리했다.

## 평가 범위와 척도

사용자 지시에 따라 **설계 완성도만 평가한다. 제출 준비도는 채점하지 않는다.**
대회의 다섯 심사 항목을 아래와 같이 설계 관점으로 해석했다. 공식 심사 점수나 수상 가능성 예측이 아니다.

- 기술 구현 → 구조, 상태 전이, 권한 경계, 실패 처리, 실현 가능성을 검증하는 계획.
- 디자인 → 사용자 흐름, 상태 설명, 실패 복구, 다음 행동.
- 잠재 영향 → 고객 문제, 대안 대비 가치의 논리, 가설 검증과 기각 조건.
- 혁신성 → 차별점의 구체성, 추가 구조의 필요성, 주장 범위.
- 발표 → 설명 순서, 시연 구성, 핵심 주장을 보여 주는 방법.

코드, 작동 UI, sandbox 기록, 인터뷰 결과, 영상, 배포, 라이선스가 없다는 이유로 감점하지 않았다.
실험 계획의 모호함과 설계 내부의 결정 누락은 감점 대상이다. 실험 미실행 자체는 감점 대상이 아니다.
GD가 제안 채택과 기존 ADR 정합성을 관리하므로, 현재 제안 상태나 미채택을 중복 감점하지 않았다.

| 점수대 | 설계 판단 기준 |
| --- | --- |
| 9~10 | 핵심 결정, 정상·실패 경계, 검증 방법이 정해져 있고 일부 세부만 남음 |
| 7~8 | 구조는 실행 가능하나 중요한 결정이나 반례가 일부 남음 |
| 5~6 | 핵심 흐름에 설계 누락이나 충돌이 있음 |
| 3~4 | 개념 중심이며 핵심 관계가 정해지지 않음 |
| 0~2 | 핵심 주장이 성립하기 어려움 |

## 결과: 38/50

**판정: 핵심 구조는 구체적이며, 일부 권한·예외 처리·가치 검증 조건을 보완해야 한다.**
기존 22/50은 설계와 제출 증거를 함께 본 평가다. 이번 38/50과 직접 비교하거나 16점의 설계 개선으로 해석하면 안 된다. 평가 대상 파일은 같은 버전이다.

| 항목 | 점수 | 인정한 설계 강점 | 남은 감점 근거 |
| --- | ---: | --- | --- |
| 기술 | **7/10** | 단일 서버·단일 지급 작업자, 원자적 한도 예약, 계정·합의·파일 결속, 응답 유실 복구, 정지 경합의 기준과 반례가 구체적임 | 지급 제출 후 기한 만료의 효력, 앱 인증과 객체별 권한, 장기 지급 불명의 처리 권한·종결 조건이 부족함 |
| 디자인 | **8/10** | 구매자·제공자의 정상 흐름과 실패·재작업·정지·전달 복구를 연결함. 상태와 가격을 먼저 보여 주고 기술 기록은 펼쳐 보도록 함 | 수동 지원과 장기 불명 상태에서 담당자, 필요한 증거, 사용자 다음 행동이 충분히 정해지지 않음 |

| 혁신성 | **7/10** | 양측 제한 위임·작업 완료 검사·지급 연결로 차별 주장을 좁히고 기존 규격과의 중첩을 인정함 | 고정 제공자와 규칙 기반 자동 지급만으로 해결되지 않는 조건이 불명확함. 협상과 양측 에이전트가 추가로 필요한 이유를 비교할 계획이 부족함 |

## 설계 지적과 최소 보완

행 번호는 위 해시의 수정안 기준이다. 아래는 구현 취약점의 발견이 아니라 설계에서 결정해야 할 항목이다.

### D1. 지급 제출 후 기한 만료의 효력이 모호하다 — 높음

근거: §6 90~94행, §8 129행.

- 발동 조건: 지급 제출 커밋 → HTTP 발송 전 종료 → 합의 기한 만료 → 재시작.
- 실패 가능성: §6은 같은 요청의 처리를 계속하도록 하지만, §8은 상태 제한 없이 기한 만료 시 지급하지 않는다고 한다. 구현과 사용자 안내가 달라질 수 있다.
- 최소 보완: 기한의 효력이 지급 제출 커밋까지인지 명시한다. 그 선택을 유지한다면 §8을 “지급 제출 전 기한 만료”로 좁힌다. 외부 승인 만료·결제 실패는 별도로 처리한다.
- 설계 검증: 이 순서를 G3 반례에 추가하고 허용 행동, 예약 유지·해제, 사용자 표시를 정한다.

### D2. 앱 인증과 객체별 권한 경계가 덜 정해졌다 — 높음

근거: §4 57~62행, §8 135~140행. 기존 ADR 0013은 사용자·에이전트 서명 열쇠를 분리하지만 앱 로그인과의 연결은 정하지 않는다.

- 발동 조건: 다른 사용자가 유효한 거래의 계정 연결 ID, 결과 파일 ID 또는 정지 대상 ID를 자신의 요청에 넣는다.
- 실패 가능성: 거래 서명과 지급 계정의 일치는 확인해도, 그 요청자가 해당 객체를 읽거나 변경할 권한이 있는지는 별개다.
- 최소 보완: 로그인 신원과 Principal을 연결하는 절차를 정한다. 계정 연결 변경, 파일 읽기, 긴급 정지, 운영자 조회의 허용 주체를 작은 권한표로 명시한다.
- 설계 검증: 다른 Principal의 객체 ID를 넣은 요청의 거부 조건을 적는다. 서버 저장 파일의 암호화 열쇠 소유·보관 주체도 정한다. 기존 사용자 서명 열쇠 정책을 새로 만들 필요는 없다.

### D3. 장기 지급 불명의 운영 절차가 부족하다 — 높음

근거: §5 74~75행, §6 87행, §8 137~139행.

- 발동 조건: 응답의 외부 ID를 받지 못했고 멱등 보관 기간이 지났다. 조회로 지급 여부를 확인할 수 없다.
- 실패 가능성: 지급을 반복하지 않는 안전 규칙은 있지만, 예약이 유지되는 동안 누가 어떤 증거를 확인하며 사용자에게 무엇을 안내할지 모호하다.
- 최소 보완: 허용하는 외부 확인 자료, 운영자 권한, 감사 기록, 상태 변경 조건, 사용자 문의·이의 제기 경로를 정한다.
- 설계 검증: 지급 완료 확인, 지급 불가능 확인, 끝내 확인 불가의 세 경우를 나눈다. 확인 불가 상태의 예약 유지는 유효한 정책이다. 종결을 위해 근거 없이 예약을 풀거나 성공·실패를 추정해서는 안 된다.

### D4. 검사 성공과 고객 가치의 연결이 부족하다 — 중간

근거: §2 24~28행, §7 98~118행.

- 발동 조건: 단색 배경 평가에서는 검사가 잘 작동하지만 실제 고객 작업 대부분에는 그림자나 복잡한 배경이 있다.
- 실패 가능성: 안전 목표를 충족해도 대부분의 의뢰를 거부하거나 초기 설정 비용이 절약 시간보다 클 수 있다.
- 최소 보완: 고객의 실제 작업에서 지원 가능한 입력 비율을 측정한다. 적용률, 건별 시간·비용, 설정 부담의 가설 기각 기준을 평가 전에 정한다.
- 설계 검증: G2 정확도와 G5 적용률·경제성을 별도로 판단한다. 고객 가치가 낮으면 고객·작업 가설을 재검토한다. 임의의 높은 성공률을 주장할 필요는 없다.

### D5. 더 단순한 자동 지급 방식과의 비교가 빠졌다 — 중간

근거: §2 24행, §8 124행, §9 146~150행.

- 발동 조건: 동일 제공자·고정 작업에 미리 정한 가격과 검사 규칙만으로 무인 거래를 수행할 수 있다.
- 실패 가능성: 양측 에이전트와 협상이 기존 자동화보다 복잡도만 늘려도 현재 비교군에서는 이를 분리해 판단하기 어렵다.
- 최소 보완: 같은 결제·검사 조건에서 고정 규칙 기반 자동 지급 흐름을 비교군에 추가한다. 조건 변경, 양측 제한 충돌 등 협상이 필요한 사례와 필요 없는 사례를 나눈다.
- 설계 검증: 양측 위임·협상이 추가로 줄이는 오류나 개입을 측정할 계획을 둔다. 추가 가치가 없으면 협상 역할이나 차별 주장을 좁힌다.

발표의 소규모 보완은 동일 거래의 합의·검사·지급을 한 화면에서 연결해 보여 주는 구성을 정하는 것이다. 실제 영상 제작 여부는 이번 감점 근거가 아니다.

## 판단의 범위

D1·D2는 G3 구현 기준을 확정하기 전에 보완해야 한다. D3~D5는 운영 완결성과 가치 판단을 보완하는 항목이다.
이 지적들은 격리된 G1·G2 타당성 실험의 착수를 막지 않는다.

실제 PayPal 계정의 무인 결제·복구 지원, 검사 정확도, 고객 수요, 실제 시연 시간은 미검증이다. 이 사실 자체는 이번 점수에서 감점하지 않았다.
새 외부 API 사실은 조사하지 않았다. 수정안 본문은 변경하지 않았으며, 이번 결과는 설계 검토 기록이다.
