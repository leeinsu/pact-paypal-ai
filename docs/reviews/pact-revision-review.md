## 최종 판정

**READY_FOR_EXPERIMENTS — 격리된 G1·G2 타당성 실험에 착수할 수 있다.**

출시 승인, 제출 적격성 확인, 구현 검증 통과를 뜻하지 않는다.
G3 거래 구현 전에는 GD에서 제안 채택과 기존 문서의 충돌 해소를 완료해야 한다.
현재 기존 ADR과 용어집의 긴급 정지 정의는 수정안과 다르다. GD를 생략하면 판정은 REVISE로 돌아간다.

## 역할과 검토 이력

기존 `metis` 역할이 모순·누락·실행 위험을 검토할 수 있어 재사용했다. 별도 에이전트 설정은 만들지 않았다.
설계 작성자와 독립 검토자는 분리했다. 검토자는 파일을 수정하지 않았다.

| 단계 | 담당 에이전트 | 결과 |
| --- | --- | --- |
| 최초 평가 전달·수정안 작성 | `pact_design_revision` / `worker` | R1~R13에 대응하는 별도 제안 작성 |
| 1차 독립 적대적 리뷰 | `pact_adversarial_review` / `metis` | REVISE. P0 2건과 P1 3건 발견. 22/50 |
| 지적 반영 | `pact_design_revision` / `worker` | C1~C5 보완, 반례와 통과 조건 추가 |
| 최종 독립 재검토 | `pact_revision_recheck` / `metis` | READY_FOR_EXPERIMENTS. 새 필수 모순 없음. 22/50 유지 |

최종 재검토는 처음에 크레딧 부족으로 중단됐다. 사용자 재개 요청 후 새 독립 검토 에이전트가 최신 문서를 읽고 위 판정을 반환했다.
이 기록은 주 에이전트가 실제 검토 결과를 정리한 것이다.

## 추가 지적과 반영 결과

아래 행 번호는 위 해시의 수정안 기준이다. “해소”는 설계 지적에 대한 판단이며 실행 검증 결과가 아니다.

| ID·심각도 | 반례와 실패 | 최소 수정과 근거 | 재검토 |
| --- | --- | --- | --- |
| C1·P0 | 지급 제출 커밋 후 HTTP 전 종료 → 긴급 정지 → 재시작. 같은 요청을 발송할지 금지할지 규칙이 충돌했다. | 지급 제출 커밋을 기준으로 통일. 정지가 먼저면 금지하고, 제출이 먼저면 동일 요청의 처리를 계속한다. 불명·멱등 기간 초과는 보류한다. §6 85~94행, G3 반례 182행 | 설계상 해소 |
| C2·P0 | 구매자 A의 서명에 사용자 C의 결제수단을 연결하거나 제공자 B와 다른 판매자 M을 연결할 수 있었다. | 양측 Principal·계정 소유자·에이전트 위임·불변 계정판을 확정 및 지급 제출 전에 대조한다. 불일치 시 해당 외부 호출을 막는다. §4 57~62행, G3 반례 181행 | 설계상 해소 |
| C3·P1 | 검사기 개발자가 평가 자료를 먼저 보고 쉬운 표본만 선택하거나 규칙을 맞출 수 있었다. | 검사기·규칙서·보정 자료 해시를 먼저 고정한다. 분리된 평가 담당자가 이후 자료를 공개한다. 첫 결과 전체를 보존하고 수정 후에는 새 평가 묶음을 쓴다. §7 112~118행 | 평가 절차상 해소 |
| C4·P1 | 임시 파일의 저장·재읽기만 성공한 뒤 결제하면 앱 재시작 시 파일을 인도하지 못할 수 있었다. | 영속 파일을 요구한다. 저장 직후 재시작의 동일 해시 읽기와 결제 후 권한 기록 전 재시작의 실제 다운로드를 필수 검증한다. 영구 소실의 수동 지원으로 통과를 대신하지 않는다. §8 135~138행, G4 183행 | 설계상 해소 |
| C5·P1 | 구현자가 승인된 ADR과 제안서 중 서로 다른 확정·정지·신뢰 규칙을 임의로 선택할 수 있었다. | GD에서 채택 기록과 ADR 유지·대체 결정을 작성하고 PACT·용어집·README를 일치시킨 뒤 G3에 진입한다. §10 168행, §12 207~209행 | 절차상 해소. 원문 충돌 해소는 GD에서 수행 |

특히 C1의 선택은 사용자에게 영향을 준다. 지급 제출이 먼저 확정됐다면 긴급 정지 뒤에도 해당 지급 처리가 계속된다. 수정안은 이 한계를 화면에 명시하도록 요구한다.

## 최초 지적 추적

R1~R13의 형식적 누락은 없다. 각 항목의 대응 위치와 필요한 증거는 수정안 §11에 있다.

- R10·R12: 기존 규격에 관한 과장과 증거 내보내기·실제 분쟁 제출의 혼동을 문구에서 해소했다. 혁신성이나 API 기능이 입증된 것은 아니다.
- R2~R7: 거래 안전과 사용자 흐름을 설계에 반영했다. G3·G4 구현 증거가 필요하다.
- R1·R8·R9·R11·R13: 결제 실험, 고객·효과 측정, 검사 평가, 영상, 제출 요건 검증을 기다린다.

## 남은 검증과 위험

| 게이트 | 필요한 증거 또는 결정 | 현재 상태 |
| --- | --- | --- |
| G1 | 실제 계정의 최초 동의 후 추가 승인 없는 후속 결제, 조회·취소, API별 멱등성과 보관 기간 | 미실행 |
| G2 | 독립 자료의 정상 결과 수락률, 악성 결과 오수락, 지원 밖 입력 거부 | 미실행 |
| GD | 수정안 채택, 기존 문서의 정지·확정·신뢰 규칙 통일 | 미채택 |
| G3 | 단일 지급, 원자적 한도 예약, 정지 경합, 계정 변경 거부, 실제 sandbox 응답 유실 복구 | 미구현 |
| G4 | 영속 파일과 접근권의 재시작 복구, 실패·재작업·정지 화면 | 미구현 |

G1이나 G2가 실패하면 핵심 주장이 성립하지 않을 수 있다. PayPal 상태 불명은 한도를 장기간 묶을 수 있다. 서버 신뢰와 호스트 전체 파일 소실 위험도 남는다.

## 같은 방식으로 후속 검토하는 절차

1. 최초 평가를 고정하고 지적 ID를 유지한다. 최신 수정안과 실험 증거를 설계 에이전트에 전달한다.
2. 설계 에이전트는 지적별 변경·남은 위험·검증 조건을 작성한다. 실험하지 않은 항목은 미실행으로 표시한다.
3. 별도 `metis` 에이전트가 읽기 전용으로 검토한다. 발동 조건 → 실패 → 문서 근거 → 최소 수정 순서로 지적한다.
4. 검토자는 다섯 기준을 각각 10점 만점으로 평가한다. 설계 결정과 실행 증거를 구분한다.
5. 설계 에이전트가 필수 지적을 반영하면 독립 검토자가 다시 확인한다. 남은 문제가 실험 증거를 요구하면 그 게이트와 실패 조건을 기록한다.
6. 검토 대상의 해시, 판정, 점수, 지적별 처리 결과를 남긴다. 실험 착수 가능 판정을 구현·출시 승인으로 바꾸지 않는다.

이번 작업은 문서 검토와 수정안 작성이다. 코드 실행, PayPal sandbox 호출, 고객 조사, 실제 영상 검증은 수행하지 않았다.
