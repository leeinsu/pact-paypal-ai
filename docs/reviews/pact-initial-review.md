# PACT 최초 적대적 설계 평가

기준일: 2026-10-20. 출처: 사용자가 수정안의 입력으로 지정한 직전 대화의 평가.
평가 대상: [PACT](../../PACT.md), [README](../../README.md), [용어집](../../GLOSSARY.md), [ADR 24개](../adr/).
이 문서는 최초 평가를 고정한다. 이후 수정안의 점수와 섞지 않는다.

## 점수와 판단

공식 심사 기준 다섯 항목은 같은 비중이다. 아래 10점 척도는 이번 사전평가의 환산 척도이며 공식 점수표가 아니다. [공식 규정 §6](https://paypalaihackathon.devpost.com/rules)

설계는 사용자에게 필요한 이유보다 프로토콜의 규칙을 더 잘 설명한다. 실제 구현이나 영상이 완성됐다고 가정하지 않았다. IDEAS.md의 과거 후보 점수는 근거로 사용하지 않았다.

## 고정 지적 목록

| ID | 최초 지적과 근거 | 필요한 변화 또는 증거 |
| --- | --- | --- |
| R1 | 핵심 무인 결제가 구현 전 확인 항목이다. PACT의 계정·토큰·수취인 구조에서 후속 결제가 된다는 증거가 없다. | 최초 동의 뒤 추가 클릭 없는 sandbox 승인·결제 기록 |
| R2 | 기간 총한도 10달러에서 6달러 거래 두 건이 동시에 통과할 수 있는지 설명이 없다. | 원자적 한도 예약·차감·해제와 동시 요청 검증 |
| R3 | PayPal 결제 후 응답 유실·프로세스 종료 시 조회·복구·재시도 규칙이 없다. 단순 재전송 방어만으로 차별성을 증명하기 어렵다. | 결제 한 번, 복구된 로컬 상태, 새 결제 생성 차단 |
| R4 | 올바른 PACT 서명에 다른 PayPal 수취인을 연결하는 공격의 방어가 부족하다. | 합의·거래 당사자·실제 결제 계정의 연결과 불일치 거부 |
| R5 | 위임 취소와 최종 서명이 경합할 때 서명 시각과 기록 확정 순서 중 무엇이 효력을 정하는지 불명확하다. | 단일 확정 기준과 취소 경합 검증 |
| R6 | 실패 상태는 있으나 작업 설정, 실패 이유, 재작업·종료, 긴급 정지 이후 처리, 결과물 접근 흐름이 부족하다. | 구매자와 제공자가 다음 행동을 알 수 있는 화면·상태 |
| R7 | 결제 전 전달은 미지급, 결제 후 전달은 전달 실패 위험이 있다. 작업 후 지급 실패도 남는다. | 인도 시점·보관·복구 정책과 제공자에게 보이는 한계 |
| R8 | 배경 제거 구매자가 왜 직접 호출 대신 에이전트 간 협상·서명을 택하는지 근거가 없다. | 고객 한 유형, 비교 대상, 시간·비용·실패 손실 측정 |
| R9 | 형식·투명 영역만으로 유효한 결과를 보장할 수 없다. 전경 보존의 방법·기준값도 없다. | 정상·전경 훼손·배경 잔존 결과를 구분하는 독립 검증 |
| R10 | 서명된 위임, 무인 거래, 결제 증거는 AP2와 중첩된다. 기존 개념의 설명이 지나치게 좁다. | 중첩 인정, 제공자 위임·이행 검사·지급 연결의 좁은 비교 |
| R11 | 영상은 첫 45초에 개념·설정을 설명하고 1분 25초부터 실제 작업·결제가 나온다. 재사용 차단만으로 핵심 가치를 보여 주기 어렵다. | 고객 문제로 시작, 잘못된 결과 지급 차단과 정상 지급 비교 |
| R12 | 증거 묶음 준비와 실제 PayPal 분쟁 증거 제출을 혼동할 수 있다. 제출 기능은 미확인이다. | 구현된 범위 표시, 실제 제출 여부의 검증 가능한 구분 |
| R13 | 문서만으로 작동 데모 요건을 충족하지 못한다. 영상은 정확히 3분이며 영어 제출 준비도 필요하다. | 실행 가능한 빌드, 3분 미만 영상, 영어 또는 영어 번역 |

R2~R5는 실제 취약점이 확인됐다는 뜻이 아니다. 이를 막는다는 주장에 필요한 설계가 빠졌다는 뜻이다.
사용자 인터뷰는 공식 필수 요건이 아니다. R8은 현재 다른 수요·효과 증거도 부족하다는 평가다.

## 공식 출처와 해석

- [대회 규정 §4·§6](https://paypalaihackathon.devpost.com/rules): 실행 가능한 데모, 3분 미만 영상, 영어 또는 영어 번역, 동일 비중의 다섯 기준. 설계만으로 제출 적격성을 증명하지 못한다.
- [PayPal 저장 결제수단](https://developer.paypal.com/platforms/checkout/save-payment-methods/): 후속 결제와 저장 범위를 설명한다. PACT 계정에서 사용 가능하다는 실증은 아니다.
- [PayPal 멱등성](https://developer.paypal.com/api/rest/reference/idempotency/): 요청 식별값을 통한 중복 처리 방어가 이미 있다. PACT는 합의 연결과 장애 복구까지 증명해야 한다.
- [Google AP2 소개](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol?hl=en), [AP2 구현 문서](https://ap2-protocol.org/ap2/implementation_considerations/): 위임·서명·영수증·판매자 역할과 중첩된다. 이는 검토자의 비교 판단이며 모든 AP2 구현의 기능을 단정하지 않는다.

최초 개선 우선순위는 R1 → R9 → R2·R3·R4 → R8 → R10·R11이다.
가장 좁은 유효 주장은 “양측의 제한된 위임 아래 합의한 디지털 작업의 완료 조건을 검사하고 PayPal 지급에 연결한다”이다.

## 미검증 범위

최초 평가에서는 문서를 변경하지 않았다. sandbox 호출, 실행 테스트, 실제 영상, 고객 인터뷰, 성능 측정, 다른 출품작 대비 순위를 확인하지 않았다.
21점은 설계 증거에 대한 사전평가이며 공식 심사 결과, 법적 판단 또는 구현 결함의 확정 결과가 아니다.
