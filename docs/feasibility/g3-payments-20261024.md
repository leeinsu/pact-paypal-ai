## Implemented boundary

[`ReservationStore`](../../pact/reservations.py) now persists account references, image terms, authorization identifiers, capture intents, settlements, and period consumption.
The store extends the [reservation implementation](g3-reservations-20261024.md).
Existing databases retain their records when the store adds these tables.

Trusted callers register immutable buyer consent and merchant references.
Registration does not authenticate account ownership or establish consent.
Finalization checks the referenced Principals and the supplied payment terms digest.
The existing G2 preflight checker verifies the source and image terms before finalization.
A reservation without those terms cannot acquire payment capability later.

Trusted transport must supply authenticated order and authorization readbacks.
The store checks their buyer, merchant, amount, currency, identifiers, authorization status, and expiry.
It prevents different agreements from sharing recorded order or authorization identifiers.
The implementation follows the official [authorization readback](https://developer.paypal.com/api/payments/v2/authorizations-get) structure.
The [order readback](https://developer.paypal.com/api/orders/v2/orders-get) supplies the corresponding buyer and payment links.
The store itself makes no HTTP request.

## Capture submission and recovery

Submission rechecks account ownership references, accepted output, stops, deadline, authorization expiry, and active reservations.
The existing G2 delivery checker validates the exact source and submitted output.
A later Mandate revocation preserves an existing agreement's obligation.
An emergency stop prevents a new capture submission.

One database transaction commits the request identifier, canonical payload, payload digest, output digest, and submission event.
Only the caller that creates this intent receives `dispatch_once` after commit.
Concurrent callers and restarted callers receive `query_only`.
The submission event binds the agreement, authorization, request, payload, and output.

The trusted payment adapter must obey this dispatch grant.
The storage primitive cannot prevent a caller from bypassing it and calling PayPal directly.
No adapter exists in this implementation.

A crash after commit can lose the initial dispatch grant before any HTTP request occurs.
Recovery still permits queries only under the accepted G1 boundary.
Stop, deadline expiry, authorization expiry, and elapsed time cannot grant another dispatch or release reservations.
The outcome can remain unknown permanently.
This behavior prevents a new local dispatch grant but does not guarantee external payment completion.

## Confirmed settlement

Trusted transport must supply authenticated capture and order readbacks.
The existing G1 recovery checker requires the expected buyer, merchant, JPY amount, order, authorization, and exactly one matching completed capture.
The capture must have `final_capture=true`.
A successful database transaction moves both reservations into consumption for their original periods.
It also stores the settlement, output digest, and confirmation event.
Repeated or concurrent confirmation consumes those reservations once.
Consumed amounts continue to count against their original period limits.

The output digest identifies the committed file.
Encrypted file storage and authorized output access remain unimplemented.
No failure-closure operation releases reservations.

## Local verification

The [payment tests](../../acceptance/transaction/test_payments.py) add 24 tests.
They cover conflicting account references, forged image terms, unconfirmed authorizations, concurrent submission, stops, expiry, and changed output bytes.
They also cover abrupt process exit, missing request identifiers, mismatched payment evidence, concurrent settlement, and injected database failure.
The full local suite passes 192 tests with no failures or skipped tests.
The [evidence record](evidence/g3-payments-local-20261024.json) contains the verification command and artifact hashes.
These tests use synthetic API dictionaries and local SQLite databases.
They make no Sandbox payment requests and access no credentials.
They do not establish authenticated API transport or external payment behavior.
G2 qualification remains limited to prepared photographic panels with uniform padding.

The previous reservation evidence retains its original hashes.
Its six artifacts remain available under [the baseline directory](evidence/g3-reservations-baseline-20261024/).
The current reservation module extends that historical revision.

## Remaining G3 work

1. Authenticate sessions and verify user signatures, agent signatures, and delegated conditions.
2. Establish account references through authenticated buyer consent and merchant registration.
3. Persist image intake limits and encrypted immutable files.
4. Persist order creation and authorization operations before external requests.
5. Connect trusted payment transport and enforce dispatch grants at that boundary.
6. Implement bounded nonpayment closure before capture submission.
7. Restore authorized access to the same output after confirmed payment.
8. Test integrated Sandbox response loss and obtain independent G3 review.
